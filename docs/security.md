# Security notes

## Tenant isolation and system mode

- **What RLS protects against.** Row level security is the second line of defence against application code that
  forgets a `workspace_id` filter. It does not protect against SQL injection (see the accepted risk below).
- **Roles.** The application role (`owlwire_app`) does not own any table, and every workspace table has RLS enabled.
  Request code runs only inside transactions opened by `withTenant`, which sets `owlwire.workspace_id` and clears
  `owlwire.system` for that transaction. The app role cannot UPDATE, DELETE or TRUNCATE `audit_log` (the audit trail
  is append-only) and cannot DELETE or TRUNCATE `workspace_keys` (rotation only updates them). Deleting a workspace
  still removes both through the foreign key cascade.
- **System mode.** Cross-tenant work (`withSystem`) turns `owlwire.system = 'on'` on for one transaction. Only
  `withSystem` in `packages/db/src/scope.ts` writes that value. `scripts/check-system-guc.mjs`, which runs in
  `pnpm lint`, rejects any other write that turns it on in `apps/`, `packages/`, `deploy/` and `docker/` (code, SQL,
  shell scripts, compose files and the Dockerfile, including `-c owlwire.system=` server options). Policies and
  triggers only read it with `current_setting`.
- **Workspace ids are generated by the server.** The caller of `createWorkspace` creates the id on the server with
  `newId()` (UUIDv7) and passes it to `withTenant`. A client never supplies the id of a new workspace.
- **Static guards.** Raw Drizzle is allowed only in `packages/db/src/**`. `@owlwire/db/system` (`SystemScope`,
  `withSystem`) is allowed only there and in `apps/server/src/system/**`. `pg` value imports and
  `@owlwire/db/migrate` are allowed only in the places listed in R91. dependency-cruiser enforces these rules
  (`pnpm depcruise`), and Biome shows them in the editor. Outside `packages/db/src/**`, the Biome plugin
  `tools/biome/no-unsafe-sql.grit` forbids `sql.raw` and any `.query(...)` whose SQL text uses template
  interpolation or `+` concatenation.

### Accepted risk (R123)

PostgreSQL does not tie custom settings to role privileges. Anyone who can run arbitrary SQL as the application role
can run `set_config('owlwire.system', 'on', true)` and read or write every tenant's rows. So SQL injection breaks
tenant isolation completely. We reduce this risk by building every query with bound parameters, through the static
guards above. These checks are textual: a setting name passed as a bound parameter is not detected. We will
reconsider a separate system database role instead of the setting in P2.3.

## Background jobs

- A job enqueued with a `TenantTx` is namespaced to its workspace. Its queue name and job key become
  `w:<workspaceId>:<name>` (`tenantJobName`), so one tenant cannot replace or block another tenant's job by key.
  `enqueueJob` stamps the payload with `_ws: <workspaceId>` and rejects a payload that already contains `_ws`.
- Workers never trust the payload for scope. `resolveJobTenant` resolves the workspace from the entity id in a system
  transaction and requires it to equal `_ws`. If `_ws` is missing or different, the job is dropped with a warning
  that logs ids only, and it is not retried.

### Accepted risk: job rows are readable by every tenant session

Graphile Worker's tables in the `graphile_worker` schema (job rows, queues, tasks and the `jobs` view) have no
workspace column, so RLS cannot isolate them. `ensureAppRole` gives the app role a `using (true) with check (true)`
policy on them, because tenant transactions enqueue jobs in the same transaction as the event row (outbox). As a
result, any session of the app role can read every job row of every workspace, including the payload and its `_ws`.
Writes are limited by the namespacing above, not by RLS.

This is accepted because repository code never reads job rows in a tenant transaction, payloads hold ids rather than
secrets or message content, and workers do not trust the row: each worker resolves the workspace from the entity id
in a system transaction and re-checks `_ws` before it acts. A new job payload must therefore hold only ids. The
integration test `packages/db/src/graphile-risk.int.test.ts` pins this state, so any change to it is deliberate and
must update this section.

## Database role check (`OWLWIRE_ALLOW_INSECURE_DB_ROLE`)

`serve` refuses to start when its database connection can bypass RLS: a superuser, `BYPASSRLS`, a member of any
superuser or `BYPASSRLS` role (it could `SET ROLE`), or the owner of any relation or schema in `public`,
`owlwire_private` or `graphile_worker`, directly or through membership. It also refuses when a `public` table with a
`workspace_id` column has RLS disabled. This is the same read-only query that `ensureAppRole` runs at migration time
(`rlsSubjectQuery` in `packages/db/src/rls-subject.ts`), run for the connection's own role. This usually happens when `OWLWIRE_DATABASE_URL` and `OWLWIRE_MIGRATION_DATABASE_URL` use the same role. For a
single-role local database, `OWLWIRE_ALLOW_INSECURE_DB_ROLE=true` lets `serve` start and logs each reason as a warning.
The opt-in is ignored when `NODE_ENV=production`, which the Owlwire image sets.

Two keyring checks stop startup in every environment. First, the keyring must hold, with the right key material, every
KEK version that wraps a stored workspace key. Second, the startup legacy upgrade tries to open every P0 (`kek_v0`)
connection secret; if any is sealed with a KEK version that is not configured, `serve` upgrades the ones it can open
and then refuses to start, naming the missing version (set `OWLWIRE_KEK_PREVIOUS` to it). A legacy secret that fails
for another reason (a corrupt row) is logged and does not block startup.
