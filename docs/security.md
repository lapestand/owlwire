# Security notes

## Tenant isolation and system mode

- **What RLS protects against.** Row level security is the second line of defence against application code that
  forgets a `workspace_id` filter. It does not protect against SQL injection (see the accepted risk below).
- **Roles.** The application role (`owlwire_app`) does not own any table, and every workspace table has RLS enabled.
  Request code runs only inside transactions opened by `withTenant`, which sets `owlwire.workspace_id` and clears
  `owlwire.system` for that transaction. The app role cannot UPDATE, DELETE or TRUNCATE `audit_log` (the audit trail
  is append-only) and cannot DELETE or TRUNCATE `workspace_keys` (rotation only updates them). Deleting a workspace
  still removes both through the foreign key cascade.
- **System mode.** Cross-tenant work (`withSystem`) turns `owlwire.system = 'on'` on for one transaction. Only
  `withSystem` in `packages/db/src/scope.ts` writes that value. `scripts/check-system-guc.mjs`, which runs in
  `pnpm lint`, rejects any other write that turns it on in `apps/`, `packages/`, `deploy/` and `docker/` (code, SQL,
  shell scripts, compose files and the Dockerfile, including `-c owlwire.system=` server options). Policies and
  triggers only read it with `current_setting`.
- **Workspace ids are generated by the server.** The caller of `createWorkspace` creates the id on the server with
  `newId()` (UUIDv7) and passes it to `withTenant`. A client never supplies the id of a new workspace.
- **Static guards.** Raw Drizzle is allowed only in `packages/db/src/**`. `@owlwire/db/system` (`SystemScope`,
  `withSystem`) is allowed only there and in `apps/server/src/system/**`. `pg` value imports and
  `@owlwire/db/migrate` are allowed only in a short list of database, worker and test modules. dependency-cruiser enforces these rules
  (`pnpm depcruise`), and Biome shows them in the editor. Outside `packages/db/src/**`, the Biome plugin
  `tools/biome/no-unsafe-sql.grit` forbids `sql.raw` and any `.query(...)` whose SQL text uses template
  interpolation or `+` concatenation.

### Accepted risk

PostgreSQL does not tie custom settings to role privileges. Anyone who can run arbitrary SQL as the application role
can run `set_config('owlwire.system', 'on', true)` and read or write every tenant's rows. So SQL injection breaks
tenant isolation completely. We reduce this risk by building every query with bound parameters, through the static
guards above. These checks are textual: a setting name passed as a bound parameter is not detected. A separate
system database role, instead of the setting, may replace this in a later release.

## Sign-in data and the auth database role

The sign-in library (Better Auth) keeps its data in the `auth_*` tables. They belong to the instance, not to a
workspace, so they have no `workspace_id` and no tenant RLS: the library reads and writes them outside any
`withTenant` or `withSystem` scope, and a system-only policy would break sign-up. Grants protect them instead.

- **What the split protects against.** It limits what SQL running on the application connection can reach: a SQL
  injection or a query bug in tenant code cannot read sessions, password hashes or tokens, or make a user an
  instance admin. It does not protect against a compromised server process, which holds the URLs (and passwords) of
  both roles.
- **Three roles.** The owner (`owlwire`) runs migrations. The application role (`owlwire_app`) runs every request,
  job and system lookup. The auth role (`owlwire_auth`, `OWLWIRE_AUTH_DATABASE_URL`) is used only by the sign-in
  library's adapter and by the `auth_user` system functions (`apps/server/src/system/users.ts`). `owlwire migrate`
  creates and grants it (`ensureAuthRole` in `packages/db/src/roles.ts`) with the same checks as the application
  role: `NOSUPERUSER`, `NOBYPASSRLS`, not a member of the owner role or of any superuser or `BYPASSRLS` role, owning
  no relation or schema. It must also be a different role from `owlwire_app`, and neither may be a member of the
  other, since `SET ROLE` would undo the split.
- **What the auth role can do.** `SELECT`, `INSERT`, `UPDATE` and `DELETE` on the seven `auth_*` tables; `INSERT` on
  `audit_log` (the instance-level `instance.admin_granted` record), which RLS still limits to system scope; and
  `EXECUTE` on the policy helper `owlwire_private.rls_allows`. It cannot read any tenant table.
- **What the application role can see.** Nothing at all in `auth_session` (session tokens), `auth_account` (password
  hashes and provider tokens), `auth_verification` (reset and email verification tokens), `auth_two_factor` (2FA
  secrets and backup codes), `auth_passkey` and `auth_rate_limit` (client addresses): every statement gets `42501`.
  In `auth_user` it may `SELECT` only `id`, `name`, `email` and `image` (`APP_AUTH_USER_COLUMNS`), which is what
  member lists show. It cannot read `is_instance_admin`, `two_factor_enabled` or `email_verified`, and cannot
  insert, update or delete users, so SQL running as the application role cannot make itself an instance admin.
  Foreign keys from tenant tables to `auth_user` still work, because PostgreSQL runs those checks as the table owner.
  `ensureAppRole` re-applies this on every migration run, after the blanket grant on `public`.
- **Startup check.** `serve` refuses to start (`AuthRoleSeparationError`) when the application role has any
  privilege on those six tables, any table-level privilege or any write privilege on `auth_user`, or `SELECT` on an
  `auth_user` column outside the list; or when the auth connection is the application role, can bypass RLS, owns
  the tables or lacks DML on any auth table (`checkAuthRoleSeparation`). `OWLWIRE_ALLOW_INSECURE_DB_ROLE` turns
  these into warnings outside production, as for the RLS check below.

### Sign-in library hardening

- Reset and verification identifiers are stored hashed (`verification.storeIdentifier: 'hashed'`), so a leaked
  `auth_verification` row cannot be replayed as a reset link. Provider access and refresh tokens are encrypted
  with `OWLWIRE_AUTH_SECRET` before they are stored (`account.encryptOAuthTokens`). Id tokens (Google) are stored as
  the provider sent them: the library does not encrypt them. They cannot be replayed to sign in, because id-token
  sign-in (`POST /api/auth/sign-in/social` with an `idToken`) is turned off for Google (`disableIdTokenSignIn`), and
  only the auth role can read `auth_account`. 2FA secrets and backup codes are
  stored encrypted (the library default, set explicitly). The email or SMS OTP method is not offered (no delivery
  function is configured); its codes are configured to be stored hashed (`otpOptions.storeOTP: 'hashed'`) should it
  ever be enabled.
- Session tokens are the exception: the library has no option to hash them, so `auth_session.token` holds the raw
  token. Only the auth role can read it.
- Telemetry is off. The library's logger is routed through our pino logger (`apps/server/src/auth/auth-logger.ts`):
  only warnings and errors are kept, URLs (which can carry tokens) and email addresses in its messages are replaced,
  and errors go through the same serializer that drops query parameters. Its default logger printed failed queries
  with their parameters, emails included.
- The origin, callback URL and CSRF checks are switched on explicitly, so they do not depend on `NODE_ENV` (the
  library turns the origin check off when `NODE_ENV=test`). Session cookies are `HttpOnly`, `SameSite=Lax`, and
  `Secure` with the `__Secure-` prefix whenever `OWLWIRE_PUBLIC_URL` is https.
- Emailed links are built from `OWLWIRE_PUBLIC_URL` and the bare token (percent-encoded), never copied from the
  library's URL. They must be https in production; with an http public URL the email is not sent and a warning is
  logged. The page the user lands on after the link must be on our own origin. A mail that cannot be built or sent
  is logged with its kind and error class only (no link, address or message) and never fails the request.
- Sign-in answers an unknown email and a wrong password with the same `401` body, and hashes the submitted password
  in both cases. Sign-up never signs in (`autoSignIn: false`): a new email, a taken email and a registration the
  registration rules refuse all get the same `200` with `token: null` and no cookie, with or without SMTP, and the
  client signs in with a second request. A password reset request gets the same answer whether or not the email
  exists. Verification and reset emails are sent in the background, after the response, so the mail server's round
  trip does not show in the response time either. Small timing differences remain (a new user is inserted, a taken
  email is not).
- **Remaining channel: the unverified-email `403`.** With SMTP on, signing in to an account whose email is not yet
  verified answers `403 EMAIL_NOT_VERIFIED` instead of `401`. It confirms that the account exists, but only to
  someone who already knows its password, and the user needs it to understand why sign-in fails. It is kept on
  purpose.

### Social sign-in, two-factor authentication and passkeys

- **Providers.** Discord, Google and GitHub are enabled only when both `OWLWIRE_<PROVIDER>_CLIENT_ID` and
  `OWLWIRE_<PROVIDER>_CLIENT_SECRET` are set; the callback is `<OWLWIRE_PUBLIC_URL>/api/auth/callback/<provider>`.
  A social sign-up goes through the same registration rules as an email sign-up (closed, invite-only, open), in the
  same hook, and gets the same personal workspace. A refused social sign-up is redirected to the error page with the
  reason code; this tells nothing about other accounts, since the caller already controls that provider identity.
- **Unverified provider addresses are refused.** A provider address that the provider reports as unverified never
  creates a user and is never linked to an existing one (`user.validateUserInfo`; the callback redirects with
  `error=account_not_linked`, see the next items). Otherwise someone could register a victim's address at a provider
  that does not verify it, sign up here first, and keep that way into the account after the victim claims it.
- **Account linking only while signed in.** A social sign-in never joins an existing account on its own
  (`accountLinking.disableImplicitLinking`), even when the provider and the local account both have the address
  verified: the callback answers `error=account_not_linked`. Otherwise anyone who controls the mailbox for a while
  could add the address to a provider account of their own, sign in through it past the password and the second
  factor, and keep that link after the owner resets the password. A user links a provider only while signed in
  (`/api/auth/link-social`), which needs a verified provider address too. No provider is trusted blindly
  (`trustedProviders` is empty), and linking a provider account with a different address is off
  (`allowDifferentEmails: false`).
- **One answer whether or not an account exists.** An unverified provider address fails differently in the library
  depending on whether an account has it: with no account, user creation is refused (`email_not_verified`, with a
  description); with one, linking is refused (`account_not_linked`). Some providers (Discord, for example) let anyone
  put an arbitrary unverified address on their account, so the difference would tell anyone whether an Owlwire
  account exists for an address. An after hook on `/api/auth/callback/*` (`apps/server/src/auth/second-factor-gate.ts`)
  rewrites both to `error=account_not_linked` with no `error_description`, on the default error page and on an
  `errorCallbackURL` alike. This applies to an explicit link while signed in too, where the code is then less
  specific. A refused social sign-up of a provider-verified address still names its reason; that address belongs to
  the caller.
- **Two-factor authentication.** TOTP (issuer `Owlwire`) with one-time backup codes; enabling it requires the account
  password. Every `/api/auth/two-factor/*` endpoint is limited to 3 requests per 10 seconds per client address, and an
  account is locked for 15 minutes after 10 consecutive failed second-factor checks from any address; a pending
  sign-in also ends after 5 failed codes. While locked, even the right TOTP or backup code is answered
  `429 ACCOUNT_TEMPORARILY_LOCKED`. Turning it off (`/api/auth/two-factor/disable`) needs the account password and a
  session that is still live in the database (a revoked or expired session is refused); it does not need a recently
  created session, because the password is asked for again.
- **Accepted risk: a TOTP code can be used more than once.** A code is valid for about 90 seconds (the current
  30-second step and one step either side), and the library keeps no record of codes already used, so a code seen by
  someone else (over a shoulder, for example) still works within that time. Using it to sign in also needs the
  account password and the pending `two_factor` cookie of a sign-in that password started; a backup code works only
  once. A guard that records used codes would have to read the plugin's internal challenge state, and
  could not be made atomic without a unique key on `auth_verification`, so two requests with the same code could
  still both pass. The cost is judged higher than the risk.
- **Where the second factor applies.** A user who has turned TOTP on is asked for it after an email and password
  sign-in (the library) and after a social sign-in (`apps/server/src/auth/second-factor-gate.ts`): the session the
  provider sign-in created is revoked and its cookies dropped, and the two-factor plugin's own challenge is issued
  instead, a signed `two_factor` cookie valid for 10 minutes. The callback then redirects to the web app's code step
  (`/sign-in/two-factor?callbackURL=…`), and a TOTP or backup code posted to `/api/auth/two-factor/verify-totp` or
  `/verify-backup-code` completes the sign-in, under the same attempt cap and account lockout. Whether the provider
  account has a second factor of its own is not something Owlwire can know, so it is not relied on. Enabling TOTP
  needs the account password, so it is available to accounts that have one. A passkey sign-in stands in for TOTP,
  because the passkey must prove two factors itself (next item).
- **Passkeys.** The relying party ID is the host of `OWLWIRE_PUBLIC_URL` and the expected origin is that URL's
  origin, configured on the server, so a response from another origin is refused (the origin a client sends is never
  used). User verification (the authenticator's PIN or biometric) is required: registration and sign-in options ask
  for it (`userVerification: 'required'`), and the server refuses any registration or sign-in response whose
  authenticator data does not report it (`USER_VERIFICATION_REQUIRED`), so a security key without a PIN cannot sign
  in on possession alone. Registering a passkey requires a fresh session. A credential id can be registered once
  (`auth_passkey_credential_id_unique`). Changing `OWLWIRE_PUBLIC_URL` to another host invalidates every registered
  passkey.

### Client address and rate limiting

Sign-in attempts are rate limited per client address, with counters in `auth_rate_limit` shared by every replica.
The library only sees a `Request`, so the HTTP mount passes the address in an internal header
(`x-owlwire-client-ip`); a value a client sends in that header is always dropped, and the library reads no other
header. By default the address is the TCP peer of the connection and `X-Forwarded-For` is ignored, because any client
can send it. Only when the peer is listed in `OWLWIRE_TRUSTED_PROXIES` (addresses or CIDR ranges) is the header read:
its hops are walked from the right, trusted proxies are skipped, and the first untrusted hop is the client; a hop that
is not an address stops the walk. Behind an unlisted proxy, every user shares the proxy's limit (a denial of service
risk, not a bypass); listing a range that also contains clients would let those clients pick their own address.

`serve` cannot see a proxy, so it guesses: the server itself speaks plain HTTP, and an `https://` public URL means TLS
ends somewhere in front of it. With an `https://` `OWLWIRE_PUBLIC_URL` and an empty `OWLWIRE_TRUSTED_PROXIES` it logs a
startup warning. A deployment that terminates TLS on the same host without a proxy can ignore it.

## Management API (`/api`)

The web UI's API is authenticated with the session cookie. Every path under `/api` requires a session except an
explicit allowlist of public routes (today only `GET /api/auth-config`), so a route added later is protected unless
it is deliberately made public; a test walks every registered route and expects `401` without a session. A path that
no route answers gets `404` before the session check, so a removed or mistyped endpoint reads as gone; the route list
is public in the open-source repository, and a path the check misses is refused rather than served without a session.
The sign-in routes under `/api/auth/*` are served by the sign-in library and are not part of this router.

Cross-site request forgery is refused in layers:

- The session cookie is `SameSite=Lax`, so browsers do not send it on cross-site `POST`, `PUT`, `PATCH` or `DELETE`.
- Request bodies must be `application/json`. A form, multipart, plain-text body or a body without a content type is
  refused with `415`; an HTML form cannot produce a JSON body, and a cross-origin `fetch` with JSON needs a CORS
  preflight, which the server never grants.
- An explicit check on every state-changing request (`POST`, `PUT`, `PATCH`, `DELETE`): a request whose `Origin`
  header is present and is not the origin of `OWLWIRE_PUBLIC_URL`, or whose `Sec-Fetch-Site` is `cross-site`, gets
  `403 forbidden` with a fixed detail. This also covers a sibling subdomain (same site, other origin), where
  `SameSite` does not help. Requests with neither header pass: browsers always send at least one of them on these
  methods, so only non-browser clients, which cannot ride a victim's cookie, omit both.

Errors are Problem Details with fixed details: framework client errors (malformed JSON `400`, a body that is not JSON
`415`) and data-layer errors never echo the request or a database value. An unknown, foreign, deleted or malformed
workspace id gets one identical `404` body.

Roles are checked twice. The access check runs before the handler, in its own transaction, so a demotion or removal
can commit between that check and the write. Every write that depends on the caller's role (renaming or deleting the
workspace, changing a role, removing a member, transferring ownership) therefore locks the workspace row first and
reads the caller's membership again under that lock. The lock is `FOR NO KEY UPDATE`: it serialises these writes, but
does not block inserts that only reference the workspace (audit entries, new memberships). Such writes run one after
another per workspace, and each decides on the roles the previous one left: a caller demoted meanwhile gets `403`, one
removed meanwhile gets `404`. The last owner of a workspace cannot be demoted or removed (`409`, detail `last_owner`);
the data layer enforces this a second time under its own row lock. An admin may demote another admin (or themselves) and
then remove them; only an owner can restore the role.

Any member can read the member list: user id, name, image, role and join date. Only owners and admins also see each
member's email; nothing else from the user record is exposed. The workspace's audit log is readable by owners and
admins only (`403` for plain members), because entries carry member and invitee details such as invitation emails. The
log shows only the workspace's own entries; an actor's name is shown only while that user is still a member.

### Invitations

Owners and admins invite by email (`POST /api/workspaces/{workspaceId}/invitations`, role `admin` or `member`), list
the pending invitations with the invitee emails and revoke them; plain members get `403`. Inviting and revoking take
the workspace lock and read the caller's role again, like the other role-dependent writes. An address that already
belongs to a member is `409 already_member`; inviting an address again replaces its pending invitation.

- The token is `ow_inv_` plus 256 random bits. Only its SHA-256 hash is stored; the plain token appears once, in the
  link `<OWLWIRE_PUBLIC_URL>/invite/<token>` (percent-encoded) in the email and in the inviter's response, and is
  never logged. Invitations expire after seven days.
- The email is sent after the invitation is stored. If it cannot be sent (no SMTP, a refused message or a failing
  server) the invitation stays and the response says `emailSent: false`, so the inviter can pass the link on. Links
  are emailed only for an `https://` public URL; plain `http://` is accepted outside `NODE_ENV=production` only.
- `POST /api/invitations/lookup` is public, because the invitee may not have an account yet; the token is the
  credential. It answers the workspace name, the invited email, the role and the expiry, which the email already
  says, and one identical `404` for unknown, revoked, accepted and expired tokens and for invitations of deleted
  workspaces. Every token is hashed and looked up the same way.
- `POST /api/invitations/accept` needs a session whose email is the invited one (`403 email_mismatch`), verified when
  SMTP is configured (`403 email_not_verified`). Acceptance takes the workspace lock that deletion takes, so it never
  joins a workspace deleted meanwhile, and locks the invitation row against a concurrent revoke. Accepting again is
  answered `200` without new audit entries.
- In `invite` registration mode an email sign-up (`POST /api/auth/sign-up/email`) must carry the invitation token in
  the `x-owlwire-invitation` request header. The sign-up hook admits it only when the token belongs to an open,
  unexpired invitation of a live workspace addressed to the signing-up email (both lower-cased); anything
  else, including a missing or malformed token and a server-side call without a request, fails closed. Knowing an
  invited address is not enough: the token is the only proof of the mailbox (it was mailed) or of the inviter's
  intent (it was handed over), with or without SMTP. A refusal gets the same `200` as any sign-up, the token is
  never logged, and the check costs the same as the public lookup. The header is a request header, not a body
  field, because the auth library validates the sign-up body.
- Only the provider redirect callback (`/api/auth/callback/<provider>`) skips the token in `invite` mode: the provider
  has verified the address, so a pending invitation for it is enough. Every other path needs the token, including
  other routes under `/callback/` and a social sign-in with an id token (`POST /api/auth/sign-in/social` with
  `idToken`), which is refused. Signing up never accepts an invitation; the client signs in and calls
  `POST /api/invitations/accept`, which checks the token and the email again.
- A personal workspace has only its owner and takes no invitations: creating one and accepting one are both
  `409 personal_workspace`.

## Instance administrators

An instance admin is a user with `auth_user.is_instance_admin` set. Only the auth role can write that flag, and the
API has no route that grants it: the only way in is the `owlwire admin create` command, which needs the server's
database credentials, so shell access to the deployment is the trust boundary.

- `owlwire admin create --email <email> [--name <name>] [--password-stdin]` migrates the database, then creates the
  user (email marked verified, no verification email) or promotes an existing one. Creating the user bypasses the
  registration mode, so a `closed` instance can get its first admin; nothing else can. The grant writes an
  instance-level `instance.admin_granted` audit entry.
- Without `--password-stdin` a random 24 character password is generated and printed once; it is never logged or
  stored in clear. A password is never accepted as a command-line argument (it would land in shell history and the
  process list). For an existing user, a password from stdin is ignored and the command says so: promoting never
  changes credentials.
- An invalid email or a password shorter than 10 characters exits with code `2` before connecting to the database.
- `/api/admin/*` requires a session of an instance admin (`403 forbidden` otherwise). `GET` and `PUT
  /api/admin/settings/registration` read and store the registration mode (`closed`, `invite`, `open`); a stored value
  overrides the edition config, and every change writes a `settings.updated` audit entry with the admin as actor.
  In `invite` mode an email sign-up needs the invitation token in the `x-owlwire-invitation` header (see
  Invitations).

At startup `serve` logs, without values, setup problems that weaken sign-in: no instance admin (with the command to
run), no SMTP (email-less personal mode), social sign-in without `OWLWIRE_PUBLIC_URL`, an `http://` public URL with
`NODE_ENV=production` (no `Secure` cookies, passkeys only on localhost, no verification or reset emails) and the
trusted-proxy case above. These are warnings: the server still starts.

## Background jobs

- A job enqueued with a `TenantTx` is namespaced to its workspace. Its queue name and job key become
  `w:<workspaceId>:<name>` (`tenantJobName`), so one tenant cannot replace or block another tenant's job by key.
  `enqueueJob` stamps the payload with `_ws: <workspaceId>` and rejects a payload that already contains `_ws`.
- Workers never trust the payload for scope. `resolveJobTenant` resolves the workspace from the entity id in a system
  transaction and requires it to equal `_ws`. If `_ws` is missing or different, the job is dropped with a warning
  that logs ids only, and it is not retried.

### Accepted risk: job rows are readable by every tenant session

Graphile Worker's tables in the `graphile_worker` schema (job rows, queues, tasks and the `jobs` view) have no
workspace column, so RLS cannot isolate them. `ensureAppRole` gives the app role a `using (true) with check (true)`
policy on them, because tenant transactions enqueue jobs in the same transaction as the event row (outbox). As a
result, any session of the app role can read every job row of every workspace, including the payload and its `_ws`.
Writes are limited by the namespacing above, not by RLS.

This is accepted because repository code never reads job rows in a tenant transaction, payloads hold ids rather than
secrets or message content, and workers do not trust the row: each worker resolves the workspace from the entity id
in a system transaction and re-checks `_ws` before it acts. A new job payload must therefore hold only ids. The
integration test `packages/db/src/graphile-risk.int.test.ts` pins this state, so any change to it is deliberate and
must update this section.

## Database role check (`OWLWIRE_ALLOW_INSECURE_DB_ROLE`)

`serve` refuses to start when its database connection can bypass RLS: a superuser, `BYPASSRLS`, a member of any
superuser or `BYPASSRLS` role (it could `SET ROLE`), or the owner of any relation or schema in `public`,
`owlwire_private` or `graphile_worker`, directly or through membership. It also refuses when RLS is disabled on any `public`
table that has a policy or a `workspace_id` column (for example `workspaces`, `apps`, `instance_settings`). This is the same read-only query that `ensureAppRole` runs at migration time
(`rlsSubjectQuery` in `packages/db/src/rls-subject.ts`), run for the connection's own role. This usually happens when `OWLWIRE_DATABASE_URL` and `OWLWIRE_MIGRATION_DATABASE_URL` use the same role. For a
single-role local database, `OWLWIRE_ALLOW_INSECURE_DB_ROLE=true` lets `serve` start and logs each reason as a warning.
The opt-in is ignored when `NODE_ENV=production`, which the Owlwire image sets.

Two keyring checks stop startup in every environment. First, the keyring must hold, with the right key material, every
KEK version that wraps a stored workspace key. Second, the startup legacy upgrade tries to open every legacy (`kek_v0`)
connection secret; if any is sealed with a KEK version that is not configured, `serve` upgrades the ones it can open
and then refuses to start, naming the missing version (set `OWLWIRE_KEK_PREVIOUS` to it). A legacy secret that fails
for another reason (a corrupt row) is logged and does not block startup.
